# Zig2

## About
Zig2 is a programming language born from the ideas of the Zig programming language, but its main goals are maximum compilation speed, absolute cross-platform compatibility, and an extremely slow rate of adding new keywords (limited to at most 1 word per standard version).

## How it achieves maximum compilation speed
* **There is NO compiler:** Zig2 is not a compiler; it is a fast translator to the C programming language. It completely cuts out the heavy compiler backend and reuses existing tools (`tcc` for metaprogramming, `gcc`/`clang` for optimization, and `mold` for parallel linking).
* **There are NO macros:** All C preprocessor macros are eliminated. They are replaced by `comptime_<N>` blocks (like in Zig), meaning that this specific action will be executed during the $N$-th compiler pass.
* **Strict Syntax Discipline:** Exactly one keyword can be added per standard version. Keywords are permanent and can never be deleted from the standard. To lock a file to a specific version, use the `-std=zig2_<number>` flag.
* **Optimization by Omission:** To tell the translator that a certain keyword doesn't need to be processed in a file, you can use the special `-without <keyword>` flag. The translator will completely ignore it, saving memory and compilation time.
* **Guaranteed Portability by Default:** All code is strictly translated under the assumption that it is 100% standard and portable. There is a special instrument to check this. 
* **Explicit Non-Portable Escape Hatch:** If you want to use unstandard/non-portable code, you must explicitly add the `_UnPortable` suffix to your standard flag (e.g., `-std=zig2_v1_UnPortable`). This choice will be permanently written into the object file's ABI.
* **C-Based Foundation:** The baseline standard and syntax are fully derived from the clean C programming language.

КОНСТИТУЦИЯ АЛГОРИТМИЧЕСКОЙ РЕСПУБЛИКИ ЯЗЫКА (ФИНАЛЬНЫЙ МАНИФЕСТ)1. Философия и Базовый ПринципДанный язык программирования спроектирован как высокоуровневый макро-диалект над LLVM IR. Его главная цель — абсолютное и пожизненное отсутствие легаси (Legacy-Free). Любое расширение языка является симметричным (обратимым) макросом, который обязан безболезненно удаляться из стандарта по решению Хранителя.Основополагающий закон развития языка: «Прежде чем блокировать чужие идеи, сами научитесь делать свои». Вся власть и ответственность в проекте автоматизированы, децентрализованы и привязаны к конкретным людям. Субъектов в виде «корпораций», «компаний» или «брендов» в проекте не существует. Вся тяжесть, сложность и ответственность переложены на плечи разработчиков фич, гарантируя абсолютный комфорт и безопасность для конечных пользователей.2. Структура Власти и Уровни Вето (Veto Levels)Управление проектом осуществляется на основе квантованной двоичной системы блокирующих сил. Каждому участнику присваивается определенный Уровень (Level), а вес его вето рассчитывается по формуле 2^(-Level):Level 0 (Вес вето = 1.0): Персональный, фиксированный и вечный уровень Автора (Хранителя Архитектуры). Абсолютное вето на любые изменения или удаления фич. Автор полностью освобожден от гонки за метриками.Level 1 (Вес вето = 0.5): Уровень Топ-Архитекторов. Для активации полного вето (1.0) требуется консолидированное согласие двух участников этого уровня. При уходе Автора из проекта его ответственность бесшовно распределяется между двумя преемниками этого грейда.Level 2 (Вес вето = 0.25): Уровень ведущих инженеров подсистем.Level 3 (Вес вето = 0.125): Уровень проверенных контрибьюторов.3. Алгоритм расчета грейда (Индекс Риска)Распределение участников по уровням вето (кроме Level 0) происходит автоматически перед каждым релизом на основе нормализации Индекса Риска (ind) конкретного человека по данным Git-истории:ind = (количество_багов ^ 2 / (количество_строк * log(время))) * (1 / карма)Количество багов в квадрате: Экспоненциальное наказание за халатность. Серийный автор багов мгновенно лишается власти.Логарифм времени: Защита от «дедовщины» и рейдерского захвата проекта. Время в проекте уважается, но его множитель сглаживается с годами, уступая место качеству работы. Также работает как фактор «прощения» былых ошибок — со временем влияние старых багов затухает.Количество строк: Метрика полезного объема кода. Наличие 0 строк блокирует расчет формулы (нет кода — нет вето).Карма Хабра (Мультипликатор): Саморегулирующийся социальный капитал. Начисляется участниками комитета друг другу за менторство, вежливое общение и техническую помощь. Токсичное поведение карается сливом кармы от сообщества, что обнуляет уровень вето инженера независимо от объемов его кода.4. Трехстадийный Конвейер Разработки (The Pipeline)Официальные чаты, флудилки и мессенджеры внутри инфраструктуры проекта заблокированы. Всё общение происходит строго асинхронно и публично в комментариях к коду. Любая фича обязана пройти три изолированные песочницы:Стадия 1: Ветка Реализации. Автор идеи обязан предоставить рабочий, компилируемый Pull Request. Идеи без кода не рассматриваются. В этой же ветке пишется код макроса для развертывания фичи. Комитет проекта имеет право помогать автору на этом этапе.Стадия 2: Ветка Верификации. Пространство математических пруверов. Макрос фичи обязан пройти полную формальную верификацию (математическое доказательство обратимости и корректности). Члены комитета активно помогают новичкам на этой стадии, доказывая теоремы и зарабатывая за это Карму.Стадия 3: Архитектурный Синод (Рассмотрение). Фича выносится на голосование.Первичный фильтр: Требуется получить 2/3 голосов «ЗА» от всего комитета по принципу «один человек — один голос».Инкубатор: Одобренная фича замораживается в Draft-статусе и лежит без изменений до следующего заседания Синода, проходя обкатку.The Last Call (День Вето): На следующем заседании звучит финальный призыв: «Кто против, предъявите вето!». Если Автор (Level 0) или участники комитета суммарно через двоичное сложение уровней сил не набрали вето весом 1.0 — фича вносится в стандарт.5. Двухслойный Слепок и Закон Зрелости ЭкранаЧтобы компиляция на машинах пользователей летала со скоростью света, при слиянии Pull Request сервер сразу генерирует два текстовых слепка: высокоуровневый человеческий код (Слепок А) и развернутый в базовый синтаксис (Слепок Б). В режиме Debug компилятор работает с человеческим кодом для удобства отладки.К развернутому Слепку Б применяются два жестких автоматических правила:Принудительное автоформатирование: Код прогоняется через жесткий форматтер, что полностью уничтожает лазейки для гольф-кодинга (сжатие кода в одну строку).Правило Экрана (Визуальный лимит): Если после автоформатирования развернутый базовый код фичи физически не влезает на один экран компьютера (не более N строк) — Pull Request отклоняется автоматически. Это означает: базовый язык еще не созрел для этой абстракции. Сообщество обязано сначала разработать более простые промежуточные макросы-кирпичики. Этот закон гарантирует, что код стандартной библиотеки всегда читаем, прозрачен и полностью открыт для человека.6. Легаси-Каторга и Ретроактивное ВетоОтветственность за баги и архитектурные тупики после релиза несет ТОЛЬКО конкретный автор Pull Request (или его соавторы из комитета, помогавшие на этапе верификации).Если со временем фича признается вредной, Хранитель (Level 0) активирует Ретроактивное Вето и вырезает её из стандарта. Поскольку макрос симметричен и верифицирован, компилятор на сервере автоматически запускает каскадный откат (Cascading Rollback) по графу зависимостей и бесшовно переписывает код всех пользователей во всем мире на базовый синтаксис. Проблема переписывания старого кода — это не проблема Хранителя, а обязанность алгоритма, заложенного автором фичи. Если код удаления содержит баг, претензии отправляются авторам инструментов формальной верификации. Если кому-то в процессе работы не хватает фич — они имеют полное право писать инлайн-вставки на чистом LLVM IR / Ассемблере, не загрязняя стандарты языка.
